# Проект 2 — MarketHub: мультивендорная торговая площадка

## Что мы строим

**MarketHub** — REST API маркетплейса в стиле Ozon / Wildberries в миниатюре: несколько независимых продавцов размещают товары в общем каталоге, покупатели ищут, кладут в корзину и оформляют заказы, администратор модерирует площадку.

В отличие от DevTalks (Blog), где все пользователи равны, здесь **три роли с разными правами** — это и есть причина, по которой в проекте появляется RBAC. Продавец не должен видеть чужие заказы. Покупатель не должен редактировать чужие товары. Администратор видит и может всё.

Проект намеренно выбран как основа для рефакторинга под **Clean Architecture** (уроки 25–27): богатый домен (`Order`, `Cart`, `Product`, `Payment`), реальные бизнес-правила, жизненный цикл заказа — классический пример, на котором Use Case-слой показывает свою ценность.

---

## Роли и что каждая может

**Buyer (покупатель)** — роль по умолчанию при регистрации:

- Просматривает каталог, ищет, фильтрует товары
- Управляет своей корзиной
- Оформляет заказ, оплачивает (mock), отслеживает статус в реальном времени
- Видит историю своих заказов
- Может отменить заказ, пока он не передан в доставку

**Seller (продавец):**

- Создаёт и редактирует свои товары (не чужие)
- Управляет остатками на складе своих товаров
- Видит и обрабатывает заказы, содержащие его товары (подтверждает, отправляет)
- Видит аналитику продаж по своим товарам

**Admin (администратор):**

- Управляет категориями
- Модерирует товары и продавцов (может деактивировать)
- Видит все заказы и полную аналитику площадки
- Обрабатывает нетипичные ситуации по платежам (webhook edge cases)

---

## Функционал

**Каталог:**

- Товары с категориями (плоский список категорий)
- Поиск по названию, фильтрация по цене и категории
- Пагинация, сортировка (цена, новизна, популярность)
- Изображения товаров (несколько на товар, одно — главное)

**Корзина и заказ:**

- Корзина принадлежит покупателю, живёт до оформления заказа
- При оформлении заказа корзина превращается в `Order` с зафиксированной ценой на момент покупки
- Нельзя заказать больше, чем есть на складе

**Оплата:**

- Mock-провайдер оплаты + webhook, имитирующий асинхронное подтверждение платежа

**Склад:**

- `stock_quantity` на товаре, уменьшается при заказе, возвращается при отмене

**Уведомления и real-time:**

- Email при подтверждении заказа и смене статуса (Celery, в фоне)
- WebSocket-канал для live-обновления статуса заказа у покупателя

**Аналитика и логи:**

- История заказов и статистика продаж продавца
- Лог действий пользователей (просмотры, добавления в корзину) — MongoDB

## Архитектура

Первую половину проекта (уроки 13–24) используем ту же **Layered Architecture**, что и в Blog — студент её уже знает, поэтому в отличие от Blog мы разворачиваем все слои сразу на уроке 13, а не постепенно.

```
API Layer (роутеры) → Service Layer (бизнес-логика) → Repository Layer (SQL) → Model Layer (SQLAlchemy)
```

На уроках 25–27 этот же проект рефакторится под **Clean Architecture** (Entities → Use Cases → Adapters → Frameworks) — так студент видит эволюцию одной и той же кодовой базы, а не абстрактную теорию.

## Бизнес-правила (закладываются с урока 13, растут дальше)

**Товары:**

- Цена и остаток — только `Numeric`/`int`, никогда `float` (ошибки округления в деньгах недопустимы)
- Удаление товара — **soft-delete** (`is_active=False`), не физическое удаление: товар может быть частью истории заказов
- `slug` генерируется из `name`, уникальность обеспечивается так же, как в DevTalks (Blog)

**Продавец и владение (полная проверка — после урока 18, RBAC):**

- До урока 18 используется `TEMP_SELLER_ID` как заглушка (аналогично `TEMP_AUTHOR_ID` в Blog до JWT)
- После RBAC: продавец редактирует только свои товары, админ — любые

**Деньги (закладывается с урока 13, критично для заказов на уроке 16):**

- `OrderItem.unit_price` в будущем хранит **снимок цены** на момент покупки — если продавец изменит `Product.price` позже, старые заказы не должны пересчитываться

## Что студент умеет после этого проекта

**Архитектурные навыки:**

- Разворачивать Layered Architecture с нуля быстро, без пошагового обучения слоям
- Рефакторить работающий проект под Clean Architecture, не переписывая всё с нуля
- Проектировать RBAC на уровне Service слоя

**Технические навыки:**

- Работа с деньгами в БД (`Numeric`, `CheckConstraint`)
- Файловое хранение и загрузка изображений
- OAuth2 + RBAC, Celery, WebSockets, MongoDB
- Docker Compose с 5+ сервисами, CI/CD

**Для интервью:**

- "Как хранить деньги в БД и почему не float?" — отвечает с примером ошибки округления
- "Как бы ты добавил роль продавца в готовую систему?" — объясняет RBAC в Service слое
- "Зачем снимок цены в заказе, если есть FK на товар?" — объясняет неизменность истории
